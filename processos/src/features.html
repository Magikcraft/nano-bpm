The optimization plane for Nano BPM

Nano runs production. Process OS watches it, reasons about better ways to run each process, proves them on real engines before anything changes, and promotes the winners gradually. A closed loop with the engine — not the LLM — as the final authority.

Observe traces→ Hypothesize variants→ Speculatively execute→ Rank & gate→ Deploy to a cohort
Flagship capability

Speculative Execution of Variant Hypotheses Live

Ask a model for better ways to run a process — then prove every suggestion on the real engine before trusting it. The LLM proposes; the engine decides.

Process OS folds production traces into a performance report (objective, per-task worker catalogue with cost / latency / quality, measured baseline) and hands that report — not a firehose of raw events — to a reasoning model. The model returns candidate variants: which worker should run each task, and optionally a restructured BPMN model.

Each candidate is then speculatively executed: every input is replayed through a fresh instance of the real engine-core — the same engine production runs — on a virtual clock, collecting end-to-end latency, cost, incidents, and correctness. A hallucinated “improvement” that does not actually measure better is caught by the numbers and ranked below the baseline; structurally invalid proposals are rejected with a reason.

  • Model-agnostic and OpenAI-compatible — points at a local llama.cpp, Ollama, vLLM, or a hosted provider; keys and egress stay inside the optimization boundary.
  • Every candidate is feasibility-gated on correctness and incident rate, then ordered by the scenario objective (cost, latency, or incidents).
  • Rejected proposals are reported, not hidden — you see what the model tried and why it was discarded.

Try it: POST /api/harness/hypothesize, or open the harness console.

Flagship capability

Cohort Deployment to Production In design

A proven variant earns a slice of real traffic before it earns all of it. Promotion is gradual, measured, and reversible.

A winning hypothesis is not flipped on globally. Process OS deploys it to a cohort — a bounded fraction of live instances routed to the new variant — while the rest continue on the incumbent. Both cohorts are measured against the same objective from the same live trace contract, so the comparison is apples-to-apples on production load rather than on a simulator.

If the cohort holds its gains and its gates, its share grows; if it regresses, it is rolled back automatically. This is the actuation half of the loop and the one place the engine exposes a control surface to the optimizer — a deliberate, auditable routing primitive rather than ad-hoc rewiring.

  • Bounded blast radius: a bad variant can only ever affect its cohort.
  • Live A/B on the objective, not a synthetic proxy — the production numbers decide whether the rollout advances.
  • Reversible by construction: every promotion step has a defined rollback.

Status: the routing/actuation primitive is specified in the design series and is the next keystone on the roadmap; today the loop runs up to ranked, gate-passing recommendations.

The substrate underneath

The two flagship capabilities stand on a small set of disciplined primitives.

Insights from the trace contract

Reads Nano over its public trace / metrics export and folds it into a per-process, per-element report: durations, queue vs. service time, bottlenecks, and incident clusters. GET /api/insights.

Real-engine simulation

The SimRunner drives the actual engine-core on a virtual clock, so measured latency, cost, and correctness transfer to production rather than modelling an approximation of it.

Live cluster measurement

The ClusterRunner acts and measures against a running multi-node cluster, unioning partition-local traces cluster-wide and sensing per-node backlog.

Queueing-model staffing

An Erlang-C M/M/c model fitted from measured per-job-type arrival and service times recommends how many workers hold a target p99 queue-wait. GET /api/harness/cluster?targetP99Ms=.

One-way dependency

Process OS runs as its own process and only ever reads Nano over HTTP. Nano never links or knows about it — run production without it and nothing changes.

Advisory by default

Everything short of cohort deployment is a recommendation. The engine and the measured numbers are authoritative; the optimizer never silently rewires a running system.

The governing principle: the LLM may propose anything, but nothing reaches production unproven. Simulation measures, gates feasibility, and cohorts contain the risk — the engine, not the model, has the final word.
