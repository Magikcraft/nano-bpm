Roadmap · research direction

Self-optimizing processes

Nano BPM is a Camunda-compatible research engine. Because it was built low-resource from the outset, it can become something more: a substrate that puts your running processes in a closed loop with static analysis and LLM reasoning — to find what’s slow or costly, propose a safer/faster variant, prove it’s equivalent, and measure the effect before it ever reaches a customer.

The idea

A process model is a hypothesis about the cheapest, fastest, most reliable way to get work done. Reality — incidents, slow tasks, the real cost of each step — is the experiment. Today a human reads dashboards and occasionally edits the model. The idea here is to close that loop with software.

Given metadata about what each task costs (compute, money, LLM tokens) and what an SLA violation costs the business, a reasoning layer can spot a bottleneck or an expensive step, hypothesize a better variant, prove it preserves the business outcome, try it on a slice of traffic or in a simulation, and keep the version that wins. Over time the system accumulates evidence about what works for your workload.

The optimization loop

Six stages, running continuously. The engine is the substrate for the two that touch execution — observe and trial — and the source of truth for measure.

StageWhat happens
ObserveStream a faithful, per-element execution trace and roll it into metrics (duration, queue vs service time, incident rate, cost).
ReasonAn LLM reads a token-budgeted performance report (not raw events) plus worst-case exemplars; statistics rank the real problems.
ProposeThe reasoner emits changes only from a constrained set of performance-preserving transforms — never free-text edits.
VerifyStatic analysis proves soundness and that the candidate reaches the same business outcomes; replay backs it empirically.
TrialSimulate the candidate against recorded traffic; if it wins, canary it to a small cohort with auto-rollback.
MeasureThe engine’s own metrics decide. Keep the winner; log the hypothesis, evidence and outcome immutably.

Why this engine can do it

Most of the hard substrate already exists, because of how the engine was built — not as a feature bolted on later.

  • It’s event-sourced. The engine already emits a fine-grained event for every element, job, incident and timer. That stream is the trace.
  • It’s deterministic. The clock is handed in with every command (apply(command, now)); the engine reads no wall clock and does no I/O. Same inputs → same events, exactly — the property replay and simulation depend on.
  • It’s tiny and embeddable. The core is a zero-dependency Rust crate that also compiles to WebAssembly — so you can run thousands of throwaway copies to simulate.
  • It already versions & routes. Idempotent deployment, process versions and create-time routing make canary a small step, not a rebuild.

Execution traces Tier A

The engine already produces the events; a trace projection folds them into a per-instance, per-element record — the shape a human, an LLM and a static analyzer can all read.

The single most useful detail it captures is splitting each task’s time into queue time (waiting for a worker) versus service time (the work itself) — because those two point at completely different fixes.

Each element entry also records incidents, retries, the variables it read and wrote (data lineage), and — once cost is wired in — the realized cost of that step. Traces export as native JSON for the reasoning layer and as OpenTelemetry spans for existing tracing back-ends.

Deterministic replay Tier B

To ask “would a different version have done better on the same traffic?” you can’t replay the old events — they were the old version’s outcomes. You replay the inputs.

Tier A is always-on and cheap. Tier B records business data, so it is opt-in per process/tenant, with retention limits and redaction.

Simulation with WASM

Because the engine compiles to WebAssembly and is a pure, deterministic, I/O-free function, you can spin up thousands of throwaway copies in a sandbox — on the server or right in a browser — and race candidate versions against real recorded traffic before anything reaches production.

A virtual clock lets a simulation advance time itself, so a day of process activity (including timers) runs in milliseconds. And because WASM is a hard isolation boundary, it’s also the safe place to run the process variants an LLM proposes — contained, with no access to the network, disk or other tenants’ data.

Cost & objective

You can’t optimize what you don’t measure. Optimization needs a real objective, and a guessed one is worthless.

  • Annotate intent on each task: execution cost, latency budget, SLA, the business cost of violating it, and — for AI tasks — candidate model options with their $/token/latency priors.
  • Record reality: workers report the actual cost back on completion (real tokens, real dollars, real latency). Expected-vs-realized is itself a signal.
  • One tunable utility combines throughput, cost, latency penalty and incident rate — with SLAs as constraints. The weights are your policy; the optimizer maximizes it.

Canary & verification — why this is safe

Autonomously changing a live business process is high-stakes. Three guard rails make it tolerable, and they keep the LLM firmly in the role of suggester, never decider.

  • A constrained transform space. The reasoner can only apply moves that change performance, not outcomes — parallelize independent tasks, cache a pure step, swap an implementation/model, tune retries/timeouts, batch. No free-text rewrites.
  • A verification gate. Before any trial, static analysis proves the candidate is sound (no deadlock, token-safe) and reaches the same business outcomes for the same inputs — backed empirically by replaying recorded traffic and diffing results.
  • Canary with auto-rollback. Only a small cohort sees the candidate; the engine’s own metrics decide, with sequential statistics and instant revert on any regression. Shadow mode (with idempotency keys) can compare without side effects.

Every change is tied to its hypothesis, evidence and experiment outcome in an immutable ledger — so there is always an answer to “why did this process change, and what did it buy us?”

Roadmap

Each step is independently useful and strictly enables the next. We start by surfacing the trace substrate that already exists.
