Where Nano fits in the stack

“Is this another Claude Code?” No. Nano is the layer underneath the coding agents — the durable runtime and the orchestration that turns a fleet of them into a self-driving software workforce. The agents run the loops; Nano orchestrates the graph that directs them.

Three layers, one runtime

Coding agents, an orchestration app, and a durable engine — each layer does one job and hands off to the next. All of it runs on your machine — or across a fleet.

Layer 1 · the workers you hire

Coding agents & tools

Interactive, single-session agents that actually edit code and run commands. Provider-agnostic and interchangeable — Nano drives whatever CLI harness you point at it, plus MCP tools and human approvals.

Layer 2 · the orchestration app

Nano Workforce (NWF)

Agent-graph orchestration for the agentic SDLC. Hand it an issue and it plans the work, fans a graph of agents out to implement it, drives every PR to review convergence against an automated reviewer, and merges it — escalating to a human only when an agent is stuck or a round cap is hit. The whole lifecycle is modelled as durable BPMN processes.

plan → fan-out review-convergence loop merge automation human escalation durable state / blackboard

Layer 3 · the durable runtime

Nano BPM engine

A BPMN orchestration engine written from first principles in Rust: one ~31 MB static binary, no JVM, no external database. It executes the process graphs, persists state through restarts and failure, and dispatches work to the agent-workers over the Falcon protocol. Small enough to start on a Raspberry Pi; scales out to an HA/FT cluster; compiles to WASM.

BPMN 2.0 execution durable / crash-safe single binary Falcon workers workstation → fleet

Nano Workforce is a Nano Urban app: the plan / implement / review / merge graph is authored as BPMN and run by the engine, so the workforce survives restarts, latency, and failure rather than living only in a chat session.

The landscape

Nano Workforce isn’t a faster coding agent — it’s a different layer. This is where it sits relative to the tools people already know.

Categories blur and vendors move fast; this is an indicative positioning map, not a scorecard. The point is the axis: single-agent tools operate one session at a time; Nano Workforce coordinates many of them durably.

Complementary, not competing

OpenCode, Claude Code and the Copilot CLI are exactly the kind of worker Nano Workforce hires. Adopting Nano doesn’t replace your coding agent — it puts a durable orchestrator around it.

“The agents are external workers you hire (any coding-agent CLI harness, e.g. the GitHub Copilot CLI). Nano Workforce owns the orchestration; the agents do the work.”
— Nano Workforce README

So the right question isn’t “Nano or OpenCode?” — it’s “which agent do I want Nano to drive?” Swap the harness without rewriting the workflow; the plan / review / merge graph stays the same.

A CI/CD analogy

If it helps: think of the coding agents as build steps, Nano Workforce as the pipeline that sequences and gates them, and the Nano BPM engine as the durable scheduler underneath.

In CI/CD terms The Nano stack
A build/test step A coding agent doing one task (Copilot CLI, OpenCode, …)
The pipeline definition & gates Nano Workforce — the BPMN plan / review / merge graph
The scheduler / runner that keeps it durable The Nano BPM engine — one Rust binary, crash-safe
